Build and attach frozen RewardMemory

Choose the released runtime path

The training route is completed reference run → traces → offline multiplier table → next run with frozen table. The RewardMemory Python class also supports neighborhood retrieval and append operations, used by analysis/demo utilities. That online retrieval path is not the frozen-table runtime and does not produce identical weights by default.

Preserve the reliability estimator

rho_k(R) = Pearson(provider_score_k, reference_outcome) within regime R
A_k(R) = rho_k(R) - mean_j rho_j(R), over the seven export tools
log_m_k = clip(eta * A_k(R) / max(tau, 1e-6), -cap, cap)
m_k = round(exp(log_m_k), 4)

Constant or insufficient-variance scores provide little reliability information; they are not proof that a provider is reliable. Runtime multiplies these raw multipliers into current adaptive gates and normalizes over current active providers. Preserve the distinction between a raw multiplier and an already normalized weight, or the port will apply base weights twice.

Prepare trace evidence

RewardTrace fields are signature, tool_scores, gates, final_reward, outcome, meta. Signature dimensions are valence, arousal, face_ratio, motion_regime, subtle. Outcome is a higher-is-better reference target, not automatically human preference. Record its source, orientation, scale, missingness, and train/evaluation split.

The supplied trace builder reads run/rl_samples/*/group_*/*_rewards.json, maps prefixed registry scores, and can join an external CSV with video_path,outcome. It defaults missing tool scores to 0.5, proxies face support from score deviations, and approximates prompt state unless taxonomy planning is requested. For a new host, prefer explicitly logged validity, face ratio, planned VAD and full sample IDs; do not call these legacy proxies exact measurements. Audit finite provider values, finite outcomes, path joins and counts before export. Replacing outcome with the fused reward itself creates circular agreement evidence.

Export with source-compatible keys

python3 scripts/build_reward_traces.py --results_dir RESULTS --runs REFERENCE_RUN --out traces.jsonl --outcome videoalign_overall
python3 scripts/export_jit_gate_table.py --traces traces.jsonl --out jit_gate_table.json --eta 1.0 --tau 0.5 --cap 1.0 --min_regime 20

RESULTS and REFERENCE_RUN are task-specific arguments, not shipped run artifacts. These scripts import the hyvideo package; GPU-free computation does not guarantee a dependency-free import. A host with another logging format should implement the same trace schema rather than blindly copying this glob layout.

Exporter's log multipliers are clipped to ±cap before exponentiation; all multipliers must be finite and positive. Nearly uniform multipliers can indicate little reliability signal.

Extend cross-run memory to custom evidence

The reusable estimator compares each provider with a documented higher-is-better outcome, centers reliability across the chosen provider set, and produces bounded raw multipliers. The seven released tools and four face/arousal cells are an implementation for video, not a universal vocabulary for private tasks.

  1. Define stable provider IDs and context fields in the host. Log sample/run identity, scores, validity, outcome provenance and configuration. Make score scales and direction explicit; no face or VAD proxies are needed when the task has different context variables.
  2. Update observation output, reflection support, trace serialization, exporter membership and runtime table lookup together. If reusing retrieval analysis, reconcile its separate tool list too. Distinguish genuinely missing evidence from an observed neutral value; define and report which valid records enter each reliability estimate.
  3. Fit on completed-run traces using a task-relevant outcome. Correlation with a proxy measures agreement with that proxy. An outcome derived from the same fused reward is circular evidence, and a provider that defines the outcome can receive a built-in advantage. Report those dependencies and use held-out, independently sourced evaluation for quality claims.
  4. Keep context partitions simple enough to have support. Set minimum counts, bounded tilts and an explicit fallback; inspect counts and variance before interpreting multipliers. The shipped exporter uses a pooled default for sparse regimes; an uncalibrated unit fallback is a separate design choice to validate.
  5. Version the table with the provider schema, reference run and outcome definition. Use a fixed table during the next run. Re-estimate only after that run completes, with comparable scales and data provenance; retain prior versions for comparison and rollback.

Different modalities, missing-value estimators or new context partitions are host extensions. The current command-line exporter and JSON runtime do not acquire those capabilities through configuration alone. Keep the source manifest pinned to the actual upstream implementation and record host modifications separately in the HTML handoff.

Attach deliberately

For the existing launcher, set REWARD_GATE_POLICY=jit and REWARD_GATE_JIT_TABLE to the exported path. For direct factory use, pass reward_gate_policy="jit" and reward_gate_jit_table=path in its configuration. Record the table hash, reference-run identity, outcome source, eta/tau/cap and support counts in the HTML handoff. Verify the hash remains unchanged across scoring. A missing or invalid table silently degrades to adaptive in the current code; the port must detect and report this if frozen-memory operation is required. Do not hot-swap a file and assume an already initialized scorer reloads it.
