Resolve capabilities before a real score

Read the checkpoint guide, provider preparation, requirements and the selected source modules. The public package includes glue code; four external provider repositories and weights are fetched separately. Importing a submodule may execute hyvideo package initialization and pull in additional dependencies, so copying emo_reward/ alone is not a verified standalone installation.

The taxonomy planner works without the optional external planner. The Gemini route requires its configured endpoint and runtime credentials; a local VLM route has different weights and memory needs. Resolve the actual backend and provider availability explicitly. Degraded fallbacks permit debugging but do not establish full-method fidelity. Keep the host's environment and weight paths; do not transplant the 32-GPU launcher or overwrite networking variables.

Implement the smallest boundary

  1. Pin the upstream source revision and retain its license and third-party notices when reusing code. Start from the source map, not a copied whole training stack.
  2. Read the contract, then adapt the example to the host's callback and error policy. Its default output is the single emo_total vector; it does not alter the optimizer.
  3. Pass real step metadata, explicit timing and a resolved provider configuration. Direct factory use accepts configuration keys; shell environment flags are translated by the existing launcher and do not universally configure a directly constructed scorer.
  4. When porting core modules into another namespace, update package imports and weight resolution deliberately. Preserve validity, fallback branches and fusion semantics before replacing providers.
  5. Test the callback with a fake scorer, then a real clip on available hardware. Attach RewardMemory only after the Reflect-only boundary is understood.

Configure the actual entrypoint

# Minimal direct-factory configuration, not a paper-reproduction recipe.
config = {
    "reward_gate_policy": "adaptive",
    "emo_reward_plan_enabled": False,
    "combine_videoalign": True,
}
adapter = EmoRewardAdapter.from_upstream(device=device, config=config)
rewards = adapter(video_paths, prompts, metadata)

The video-path adapter example defines EmoRewardAdapter. Device, paths, prompts and metadata come from the host. Resolve the remaining provider weights and timing intentionally; direct defaults differ from the shell recipe.

For the registry, the flat scorer configuration instead belongs under models.emo_reward.emo_reward_config, with model weight 1.0 and sub_reward={"emo_total": 1.0} for a single-model setup. Test configuration routing before adding other registry models: this snapshot's multi_video_score constructs emo_reward_config from a weight_config variable retained from its preceding parsing loop. With several models, that can select another entry's configuration. Prefer the direct factory for a new host, or repair and test routing in the host explicitly. This kit leaves upstream runtime code unchanged.
